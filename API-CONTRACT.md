# Bookmark App API contract

Approved: single user, LAN only, a few hundred bookmarks. React + FastAPI + SQLite, one container. Auto directories max 3, manual deeper allowed, max 5 AI tags, manual classification protected. Excerpt max 12000 chars. All API errors use FastAPI detail. Dates ISO strings. Server listens 8000, Docker host default 8093. Frontend built to web/dist served by backend. Local Vite proxies /api to localhost:8000.

Authentication: GET /api/auth/status -> {initialized: bool, authenticated: bool}. POST /api/auth/setup {username,password} (only once) -> {username}; POST /api/auth/login same -> {username}, both set httpOnly session cookie; POST /api/auth/logout. GET /api/auth/me -> {username}. Session cookies must support LAN HTTP, SameSite=strict. Browser API mutating calls protected by Origin validation; extension token bearer only scope bookmark save + health. GET /api/health public -> {status:'ok'}; GET /api/connection authenticated cookie or bearer -> {status:'ok'}.

HTTP caching: all `/api/` responses, including public authentication status, authenticated data, write results, and error responses, send `Cache-Control: no-store`. The web API client always uses Fetch `cache: "no-store"` and adds a fresh, nonsecret `_fresh` query parameter to each GET/HEAD request. The server ignores that parameter; it prevents a forced URL-based proxy cache from replaying an older response even when cache directives are ignored. Delete/restore must be reflected by the next read of the same logical query. Reverse proxies MUST disable caching for `/api/` and clear pre-existing API cache entries: a fresh client URL cannot secure old cached authenticated responses that a proxy serves without contacting the application. This policy does not change static asset caching or the bounded in-memory semantic query-vector cache.

GET /api/tokens -> [{id,name,created_at}]; POST /api/tokens {name} -> {id,name,token} (shown once); DELETE /api/tokens/{id}.

Bookmark shape {id,url,title,description,excerpt,summary,notes,folder_id: number|null,tags:string[],source_folder,classification_status:'pending'|'done'|'failed',manual_classification:bool,deleted_at:string|null,created_at,updated_at,error?:string}. GET /api/bookmarks?q=&folder_id=&include_children=false&tag=&trash=false&pending=false&mode=keyword|semantic -> {items:Bookmark[],total:number,warning?:string}. include_children=true with folder_id includes that folder and all descendants; the default remains exact-folder filtering. Search/tag/pending/trash filters still intersect the selected scope. POST /api/bookmarks accepts {url,title?,description?,excerpt?,notes?,folder_id?,tags?}, accepts extension bearer; -> {bookmark:Bookmark,duplicate:bool}. Duplicate normalized URL leaves previous metadata unchanged, includes trash items. PATCH /api/bookmarks/{id} accepts title/notes/folder_id/tags, protects manual classification when folder or tags present; DELETE soft deletes. POST /api/bookmarks/{id}/restore. POST /api/bookmarks/{id}/refresh {title?,description?,excerpt?}, explicitly updates metadata and invalidates embedding. New browser-session saves without manual classification still auto-queue classification when configured; imports and extension bearer saves never auto-queue classification.

GET /api/folders -> [{id,name,parent_id:number|null,bookmark_count:number,direct_bookmark_count:number}]; bookmark_count counts active bookmarks in the folder and all descendants, excluding trash and unfiled items; direct_bookmark_count counts active bookmarks assigned directly to that folder. Both reuse one grouped bookmark query. POST /api/folders {name,parent_id?}; PATCH /api/folders/{id} {name?,parent_id?}; DELETE /api/folders/{id} moves contained bookmarks to pending/unfiled and must avoid dangling children. UI manual operations are explicit confirmations; directory bulk AI reorganization preview: POST /api/folders/organize-preview -> {preview_id,changes:[{folder_id,name?,parent_id?}],description}; POST /api/folders/organize-apply {preview_id} executes stored validated preview, no model mutation before confirmation.

Directory deletion in management uses the same preview/apply flow for one or multiple folders. POST /api/folders/delete-preview {folder_ids:[positive integer]} returns {folders_deleted,bookmarks_affected,active_bookmarks_affected,trashed_bookmarks_affected,descendant_bookmarks_preserved,children_reparented,snapshot}. Counts deduplicate selected folders: affected bookmarks are assigned directly to selected folders; surviving descendants' active bookmarks are counted separately and retain their folder. The preview does not write. The UI shows the exact effects and requires a separate acknowledgement checkbox when affected or descendant bookmarks exist. POST /api/folders/bulk-delete {folder_ids,snapshot?} checks a supplied 64-hex snapshot inside the write transaction and returns 409 without writes if the selected tree or its bookmark identities/revisions changed. Unrelated trees do not invalidate it. Rechecking changes the preview and resets acknowledgement. Snapshot omission and DELETE /api/folders/{id} retain legacy API compatibility; the management UI always sends a snapshot. Delete only removes selected folders, moves their directly assigned active bookmarks to the inbox, preserves trash status, and reparents surviving children to the nearest surviving ancestor.

Directory bookmark migration: POST /api/folders/move-bookmarks-preview {source_folder_id:positive integer,target_folder_id:positive integer,include_children:boolean=true} -> {bookmarks_to_move,already_in_target,folders_included,snapshot}. Source and target must exist and differ. The scope contains active bookmarks directly in the source, plus descendants when include_children=true. Existing target bookmarks are counted separately and skipped, including when the target is a descendant of the source. POST /api/folders/move-bookmarks with the same fields and the returned snapshot -> {moved,already_in_target,folders_included}. Preview never writes; apply validates the exact folder/record scope and revisions in one write transaction, returning 409 with no changes if the preview is stale. The operation preserves the directory tree and all bookmark content/IDs, excludes trash, and marks moved bookmarks manually classified/done with cleared classification errors. Ordinary queued classification skips them and in-flight classification cannot overwrite a newer manual revision; an explicitly forced future classification retains its existing override semantics. Existing text embeddings remain valid. Both endpoints require the administrator session and same-origin protection; extension bearer tokens cannot migrate folders.

## Extension collection and inbox views

Management labels are 全部书签 (all active bookmarks, including unfiled) and 待整理箱 (active bookmarks with folder_id=NULL, regardless of AI classification status). Both navigation labels use four Chinese characters; individual bookmark status remains 待整理. These are an overview and its subset, not mutually exclusive directory categories. The pending view does not apply a remembered directory filter or offer a directory selector. Its explicit AI-organize action scopes candidates to unfiled bookmarks; manual classifications retain their existing protection.

Extension POST /api/bookmarks requests authenticated with an extension bearer token save newly collected pages without scheduling an automatic classification job, even when AI is configured. The extension sends no folder assignment by default: new captures have folder_id=null and classification_status=pending until the user assigns a folder or explicitly launches classification. Existing duplicate URLs retain their folder/content/status and are never pulled back into the inbox. Offline retries use the same endpoint and behavior. Bearer responses remain limited to {bookmark:{id,url},duplicate}; existing session-auth save/import/export/auth behavior is unchanged. No migration or reset of existing bookmark records is performed.

## Bookmark list read options

`GET /api/bookmarks` keeps its existing unpaged, complete `Bookmark` response by default. All views share the same directory/descendant/tag/pending/trash scope and Unicode casefolded literal substring search, including body text and decoded tags. List reads use batched SQL rather than one query per bookmark. Active bookmarks share one persisted global display order across scopes, full/summary/ID views, pagination and enjoy mode. Before the first drag, order remains `created_at DESC, id ASC`; later, new items without a position lead the saved manual order. Trash retains chronological ordering. Semantic search still sorts by relevance, with display order only breaking ties.

POST `/api/bookmarks/reorder` `{bookmark_id:positive integer,target_id:positive integer,placement:'before'|'after'}` moves one active bookmark immediately before/after another in the global order. A single transaction checks both IDs and updates only `sort_order`, preserving content, timestamps, folder assignment, classification, embeddings and jobs; missing/trashed IDs return 409 without writes. Hidden bookmarks retain their relative order. POST `/api/folders/reorder` `{parent_id:positive integer|null,folder_ids:positive integer[]}` stores a complete, unique sibling order. Missing/new/cross-parent entries return 409 without writes; duplicate IDs return 422. Neither endpoint changes directory hierarchy, and both require the admin session and Origin protection. Directory clients use saved sibling positions first, then Chinese name ordering for unsorted siblings (legacy pending folders default last), walking parents before descendants. Explicit drag order overrides the pending-name default. All selectors, management and enjoy catalogs share this rule. Newly created or explicitly reparented folders append after saved siblings. JSON backups include nullable `sort_order`, restore positions on newly imported records, and accept legacy backups without the field; merging duplicate records preserves existing positions.

- `view=summary` omits `description`, `excerpt`, `summary`, `notes`, and `error`, and marks each item `details_loaded:false`. All remaining metadata, tags and classification flags are retained. The web UI requests this view in both modes.
- `page` is an optional one-based page number. When present, the response also includes the effective `page` and `page_size`; `total` is the full filtered count. Pages past the end clamp to the last existing page, and an empty result reports page 1. `page_size` is 1–100, default 20. Without `page`, all matching items are returned, preserving the continuous enjoy deck.
- `include_ids=true` adds `ids`, the IDs of the **entire** matching scope in result order, independent of the requested page. Counts, IDs and page rows share one short SQLite read snapshot. This supports selecting all current results without loading full records.
- `view=ids` returns `{items:[],ids:number[],total:number}` for the entire scope, suitable for bulk-job previews without downloading bodies. IDs cover the full scope even when a page is supplied.
- `GET /api/bookmarks/{id}` returns a complete record, including a trash record when requested by ID. It requires the administrator session; extension bearer tokens cannot read lists or details. Missing records return 404.
- Semantic ranking is applied before pagination. Missing-index warnings and keyword fallback retain the same filters. An optional `search_id` groups page turns of a single search: its query vector is reused for up to 120 seconds in a per-app, in-memory cache of at most 32 entries. A new search ID or active model/credential configuration uses a new model request; no cache is written to disk. The web UI changes this nonsecret ID on search/scope changes or explicit refresh. Ranking and returned data are always read fresh.

Management uses server pagination (10/20/50 per page); enjoy requests all lightweight cards. Opening details or an edit/refresh form reads the complete record on demand. Switching scope/page cancels obsolete list reads; closing details cancels pending detail reads. Delete/restore reload the current server page and preserve only failed/conflicting IDs that still belong to the result scope.

GET /api/settings -> {classification:{base_url,model,has_key,prompt},embedding:{base_url,model,has_key},concurrency:2,send_excerpt:true,index_status:{...}}. PUT /api/settings same nested fields; api_key omitted retains key, empty explicitly clears; never return api_key. URLs configurable OpenAI bases (/v1 etc); frontend labels clarify service-side keys and text sharing. Settings model/prompt changes do not automatically reclassify history. Embedding change marks rebuild needed, old active index stays until new rebuild completes.

POST /api/import/html multipart file + mode= reorganize|preserve -> {imported,duplicates}; preserves source directory. POST /api/import/json multipart file -> {imported,duplicates}, full application data restore/merge (folders/bookmarks/settings excluding secrets). GET /api/export/html download; GET /api/export/json download, include schema_version/folders/bookmarks/settings (no API keys, auth credentials or tokens); includes trash in JSON only.

POST /api/jobs {kind:'classify'|'fetch'|'reindex',bookmark_ids?:number[],force?:bool} -> Job; defaults active pending for classify, all active for fetch/reindex, force explicit overrides manual protection. GET /api/jobs -> Job[]; POST /api/jobs/{id}/pause|resume|retry -> Job. Job {id,kind,status:'queued'|'running'|'paused'|'completed'|'failed',total,completed,failed,error?,created_at}. Tasks durable SQLite, interrupted jobs resumable after restart. Worker configurable concurrency 1..5. Model failure does not block saving; bounded automatic retry then manual retry. Fetch public HTTP/S with redirect/DNS/private IP checks, response/excerpt bounds, plain text extraction. Reindex staged publication only all succeeded, dimension validation; failed rebuild leaves old index intact. Semantic search calls embedding model once per query, keyword fallback with warning on model failure; classification result reuse existing paths before auto create <=3 levels. Server AI path treats page content as untrusted. Background purges deleted >30days.

## Running version and update checks

GET /api/version?check=false&force=false requires the administrator session (extension tokens cannot use it). Returns {version,revision,repository,status,latest_version,checked_at,error,release_url}. Version/revision/repository come from immutable backend/_build.json generated during the image build, independently of deployment tag aliases. Missing build metadata is development, never a guessed release version. No database data is read or modified.

With check=true, the server reads only https://api.github.com/repos/{repository}/git/matching-refs/tags/v using an anonymous request with a bounded timeout/body. Only stable vMAJOR.MINOR.PATCH tags count; compare numeric components, never lexicographic order. No bookmark data, credentials or registry hostname is sent. Success cache: six hours; error cache: five minutes. force=true bypasses those caches after a one-minute minimum interval; concurrent checks share one result. A normal check=false read does not contact GitHub and expires stale results.

status is unchecked | latest | update_available | ahead | unknown | development | disabled. latest requires a successful, unexpired check and equality; ahead indicates the running version is newer than the published tags. Empty tags, invalid responses, rate limits and network errors produce unknown, never latest; any previously known latest_version is retained only as historical information. CHECK_UPDATES=false disables all outgoing checks. Development builds never make outgoing checks. Transport responses use the normal no-store policy and client _fresh bypass.

The release command may opt into RELEASE_GIT_REMOTE=origin: derive the public GitHub repository from that remote, embed it in the image and push a stable version tag pointing to the exact built source only after the version image and latest digest are verified. A failed build never publishes the tag. Tag synchronization failure reports a partial release and preserves an explicit retry command; it must never claim complete success. Without this option, automatic update checks are disabled for that publisher's images. Git tag publication shares the source with the configured remote, so only enable it for public release source.

## Conversational classification assistant

All assistant endpoints require the administrator session and existing Origin protection; extension bearer tokens cannot use them. They use the configured classification model. Discussion and preview never create folders or change bookmarks.

- POST /api/classification-assistant/chat {messages:[{role:'user'|'assistant',content:string}],rules:string} -> {reply:string,rules:string}. Bounded conversation history, current rule draft and existing directory context; returns a reply and editable reusable classification rules. Client-supplied system roles are forbidden.
- POST /api/classification-assistant/preview {bookmark_ids:number[],rules:string} -> {items:[{bookmark_id,title,url,current_path:string[],path:string[],tags:string[],summary,reason,manual_classification:bool,preserve_import_folder:bool}],rules:string}. Maximum five samples; UI previews the first three selected bookmarks. A single model request classifies unprotected samples. Manual rows stay unchanged; imported-folder protection retains the current directory.
- POST /api/classification-assistant/rules {rules:string} -> {rules:string}. Saves only classification.prompt, retaining model credentials and other settings; does not enqueue work.
- POST /api/classification-assistant/apply {bookmark_ids:number[],rules:string,save_rules:bool} -> {job:Job,skipped:number}. Creates a standard classification job with a snapshot of the draft rules, skips manual classifications and retains import-folder protection. save_rules also saves the prompt for later jobs; false keeps the global prompt unchanged. Retrying this assistant job retains its rule snapshot.
